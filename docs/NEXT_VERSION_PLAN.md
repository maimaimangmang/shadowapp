## 2. v0.1.1 优先修复：账号列表错误后的恢复

**已复现**：`Sources/CodexMulti/AppModel.swift` 的 `refresh()` 在读取异常后将 `registryAvailable` 置为 `false`，随后每次刷新都会在入口直接返回。即使修复原文件，操作仍保持禁用。

复现结果如下。

```text
Initial registry available: true
After invalid registry: false
After restoring valid registry and refreshing: false
Store can read restored registry: true
```

**建议实现**：提供明确的“重试读取”操作。读取成功后重新启用界面并计算实例状态；读取失败时继续保留原文件和禁用相关操作。避免定时器反复弹出同一个错误。

**通过标准**：损坏文件不被覆盖；恢复有效文件后无需重启即可继续管理；失败期间不能启动或移除空间。补充针对状态转换的回归检查。

## 3. v0.1.1 优先修复：失败原因可见

**代码检查发现**：

- 自动查找应用时，兼容性检查失败不会写入界面错误；用户只看到通用的“先选择 Codex 应用”，难以区分未安装和已安装但不兼容。见 `AppModel.check(urls:reportFailure:)`。
- 菜单栏可以启动账号，但错误展示仅绑定在 `Dashboard` 的 alert；菜单没有自己的错误入口或显示主窗口的处理。关闭主窗口时失败原因是否可见，需要 UI 复现确认。

**建议实现**：保留最近一次检测失败原因，提供重新检测入口；菜单栏操作失败时显示可见反馈或打开主窗口呈现错误。

**通过标准**：未安装、应用标识不匹配、缺少目录支持、启动超时和账号列表异常均有明确提示；主窗口关闭时也能看到菜单栏启动失败原因。诊断内容不读取或输出令牌、邮箱、会话正文。

## 4. 后续稳定性工作：异常启动与数据操作

以下属于代码检查发现的风险或既有限制，本次没有把它们列为已复现故障。

- 启动中的占用标记只在当前启动器进程内；注册表锁只覆盖单次文件操作。两个启动器进程同时操作同一空间的竞争需要合成测试。根据结果决定增加空间级操作锁，或明确限制只运行一个启动器。
- 启动后、记录进程身份前崩溃会留下未跟踪实例，架构文档已有说明。优先提供清楚的恢复指引；自动接管前仍必须验证进程身份与空间归属。
- `ProfileStore.moveToTrash()` 先移动目录，再保存注册表；保存失败时会留下仍在列表中、数据已经移至废纸篓的空间。应验证失败恢复方案，避免用户再次启动后误以为历史消失。

测试应使用临时目录、合成数据和可控故障，覆盖并发启动、失败的注册表保存和恢复路径。
